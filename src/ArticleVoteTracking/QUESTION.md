# Article Vote Tracker (Rippling SDE2, LLD coding round)

**Where it shows up:** phone-screen coding, onsite coding, and as the Part 2 coding follow-up after the news-aggregator system design.

## Problem framing

> "We're building the voting backend for an internal news feed. Employees read articles, and they can upvote or downvote them. Product wants to see what each user has been voting on recently, show each article's score, and later rank the top articles. We'll start simple and add requirements as we go. Keep it in memory and in a single process unless I say otherwise. I care about clean modeling more than clever tricks."

### Questions to ask before you code
| Question | Answer |
|---|---|
| Are user and article IDs strings or longs? Do I validate that they exist? | Strings. Any ID is valid, and there's no registry. |
| Timestamp or sequence number? | A global, monotonically increasing `long seq` generated by the system. |
| Single-threaded? | Yes for Parts 1–5. Concurrency is a discussion question. |
| Invalid input, such as a null vote type? | Throw an exception (`IllegalArgumentException` or `NullPointerException`). |

### Core modeling idea
Keep two concepts separate:
- **Current state:** `(user, article) → vote`. It turns a repeated vote into a no-op.
- **Action history:** append-only and **bounded**, for example a deque capped at 3 per user or per article, so storage doesn't grow.

Reads must never create state for unknown users or articles.

## Part 1: Core voting and a user's last 3 votes (~20 min)

```java
enum VoteType { UP, DOWN }

record VoteEvent(String articleId, VoteType voteType, long seq) { }

interface VoteTracker {
    void vote(String userId, String articleId, VoteType type);
    List<VoteEvent> getLastVotes(String userId);   // last 3, most recent first
}
```

**Rules**
1. A user's first vote on an article creates an event.
2. Repeating the same vote on the same article does nothing: no event, and `seq` doesn't advance.
3. Changing a vote (UP→DOWN or DOWN→UP) creates a **new, separate** event.
4. `getLastVotes` returns at most 3 events, **most recent first**. If the user has fewer, return what exists. If the user is unknown, return an empty list.
5. **A read must not create state.** Calling `getLastVotes("ghost")` must not add an entry to any map.

**Example**
```
vote(u1, A, UP)     -> event seq=1
vote(u1, A, UP)     -> no-op
vote(u1, B, DOWN)   -> event seq=2
vote(u1, A, DOWN)   -> event seq=3 (flip)
vote(u1, C, UP)     -> event seq=4
getLastVotes(u1)    -> [(C,UP,4), (A,DOWN,3), (B,DOWN,2)]
getLastVotes(u2)    -> []

vote(u1, X, UP); vote(u1, X, DOWN); vote(u1, X, UP)
getLastVotes(u1)    -> [(X,UP,s3), (X,DOWN,s2), (X,UP,s1)]   // 3 separate events, same article
```

**What the interviewer checks**
- State and history are kept separate. A single map per article can't hold history.
- History is bounded **when you write**. Don't store everything and trim or sort when you read.
- Events are immutable. Use a `record`, and don't mutate events you've already returned.

**Common traps**
- `getOrDefault(key, new X())` returns the default but **doesn't store it**. On the write path, use `computeIfAbsent`.
- `LinkedHashMap.put` on an existing key **doesn't move it to the end**.
- A per-article counter can't order events across articles. Use a global sequence number.

## Part 2: Scores and NONE (un-vote)

```java
enum VoteType { UP, DOWN, NONE }   // NONE = clear your vote

int getScore(String articleId);    // ups − downs, O(1)
```

**Rules**
- `NONE` clears the user's vote. It's a recorded action, but it is **not** a flip (that matters in Part 3).
- **A missing vote counts as `NONE`.** So `vote(u, A, NONE)` with no prior vote does nothing.
- Any real change (old ≠ new) creates an event in `getLastVotes`, including changes to or from `NONE`.
- The score is updated by `delta = value(new) − value(old)`, where UP = +1, DOWN = −1 and NONE = 0.
  - UP→DOWN: −2
  - UP→NONE: −1
  - NONE→DOWN: −1
- An unknown article has a score of 0, and reading it creates no state.

**Example**
```
vote(u1, A, UP)     score(A) = 1
vote(u2, A, UP)     score(A) = 2
vote(u1, A, DOWN)   score(A) = 0
vote(u2, A, NONE)   score(A) = -1
vote(u2, A, NONE)   no-op, score(A) = -1
vote(u3, A, NONE)   no-op (never voted), score(A) = -1
getLastVotes(u2)  -> [(A,NONE,s4), (A,UP,s2)]
getScore("ghost") -> 0
```

**What the interviewer checks**
- The `+1/−1/0` mapping lives **on the enum**, not in an if/else ladder.
- "Missing means NONE" makes the no-op check one line. Don't add a sentinel like `DEFAULT(-2)`.
- The score update is a single `merge(articleId, delta, Integer::sum)`.
- **Discussion:** when a vote is cleared to NONE, should the state entry stay or be removed? Removing it saves memory, and "missing means NONE" makes that safe.

## Part 3: The last 3 flips per article, with every operation in O(1)

```java
record FlipEvent(String userId, VoteType fromVote, VoteType toVote, long seq) { }

List<FlipEvent> getLast3Flips(String articleId);   // oldest -> newest
```

**Definition of a flip:** only UP→DOWN or DOWN→UP. These are **not** flips:
- the first vote (NONE→UP)
- clearing a vote (UP→NONE)
- re-voting after clearing (NONE→DOWN)

**Requirements**
- Flips are tracked **per article**, across all users.
- `vote`, `getScore` and `getLast3Flips` all run in **O(1)**.
- Flip history per article is capped at 3 entries.
- **The order is oldest→newest**, the opposite of `getLastVotes`. Read the spec carefully.
- A flip event uses the same `seq` as the matching user `VoteEvent`.
- An unknown article returns an empty list and creates no state.

**Example**
```
vote(u1,A,UP); vote(u1,A,DOWN)    -> flip(u1, UP->DOWN, s2)
vote(u2,A,DOWN); vote(u2,A,UP)    -> flip(u2, DOWN->UP, s4)
vote(u1,A,NONE)                   -> not a flip
vote(u1,A,UP)                     -> not a flip (NONE->UP)
vote(u1,A,DOWN)                   -> flip(u1, UP->DOWN, s7)
vote(u2,A,DOWN)                   -> flip(u2, UP->DOWN, s8)
getLast3Flips(A)       -> [s4, s7, s8]
getLast3Flips("ghost") -> []
getScore(A)            -> -2
```

**What the interviewer checks**
- `vote()` now does four things: update state, update the score, record a user event and record a flip. Keep it readable: compute `prev` and `next` once, then call a small private method for each piece.
- Flip detection is on the enum, for example `prev.isFlip(next)`, which returns `this != NONE && other != NONE && this != other`.
- Use a `Deque` per article: `addLast`, then `removeFirst` once it holds more than 3. Copying it gives oldest→newest order directly.
- Return copies (`List.copyOf`), never `subList` views of internal state.

## Part 4: Top-K articles by score

```java
List<String> getTopK(int k);   // highest score first, ties by articleId ascending
```

**Rules**
- Order by score, highest first. Break ties by `articleId` ascending.
- An article is ranked once it has received any vote, even if its score later returns to 0 or goes negative.
- `vote()` must stay at **O(log n)**, where n is the number of articles.
- `getTopK(k)` runs in **O(k)** (or O(k log n)).
- If `k` is larger than the number of ranked articles, return all of them. If `k <= 0`, return an empty list.
- A no-op vote doesn't touch the ranking.

**Example**
```
vote(u1,A,UP); vote(u2,A,UP)                   A=2
vote(u1,B,UP)                                  B=1
vote(u1,C,DOWN)                                C=-1
vote(u2,B,UP)                                  B=2 (ties with A)
getTopK(2)  -> [A, B]                          tie broken by id
vote(u3,C,UP); vote(u4,C,UP); vote(u5,C,UP)    C=2
vote(u1,A,DOWN)                                A=0
getTopK(3)  -> [B, C, A]
getTopK(10) -> [B, C, A]
getTopK(0)  -> []
```

**Approaches**
| Approach | Update | Top-K | Notes |
|---|---|---|---|
| `TreeSet<Ranked(id, score)>` with comparator `(score desc, id asc)` | O(log n) | O(k) | **Remove the entry before changing the score**, then re-insert it. Use an immutable record. |
| Buckets: `TreeMap<Integer, TreeSet<String>>` (score → articles) | O(log n) | O(k) | The inner set must be a `TreeSet` for the tie-break. **Remove empty buckets.** |
| `PriorityQueue` | O(n) to remove | — | Removing an arbitrary element is O(n), and lazy deletion makes reads messy. **Rejected.** |
| Doubly linked list of buckets plus an `article → bucket node` map (the "All O(1)" / LFU structure) | O(1) | O(k) | Fastest, but sorted ties need a sorted set per bucket (O(log m) again), and it's a lot of code for 45 minutes. Mention it as an optimization. |

**Why Tree structures and not Hash structures?** `HashMap` and `HashSet` have no order. `TreeMap` and `TreeSet` keep keys sorted, at a cost of O(log n) per operation. `getTopK` needs scores in descending order and ties sorted by id, so both levels need a Tree structure. Maps that are only looked up by key stay `HashMap`.

**Common traps**
- **The first vote has no old bucket.** Check `articleVoteCount.containsKey(articleId)`, not `oldScore == 0`, because an article with score 0 is still ranked.
- **Read the old score before writing the new one.** Otherwise the delta is applied twice.
- **Don't reverse twice.** A `TreeMap(reverseOrder())` iterated with `descendingMap()` comes out ascending.
- **`return` inside `forEach` doesn't stop the loop.** It only exits the current lambda call. Use a plain `for` loop so you can stop early.

## Part 5 (locked variant): Recent unique flips per user

```java
List<FlipEvent> getRecentUniqueFlips(String userId);   // most recent first
```

**Rules**
- Return the user's most recent flip on each article, for their last **3 distinct articles**.
- If a user flips article A three times, A appears **once**, with its latest flip, and moves to the front.
- A flip has the same meaning as in Part 3: UP↔DOWN only.
- Order: most recent first.
- `vote` and `getRecentUniqueFlips` are both O(1).
- An unknown user returns an empty list and creates no state.

**Example**
```
vote(u1,A,UP); vote(u1,A,DOWN)    flip A  s2
vote(u1,B,DOWN); vote(u1,B,UP)    flip B  s4
vote(u1,A,UP)                     flip A  s5   (A moves to the front, replacing s2)
vote(u1,C,UP); vote(u1,C,DOWN)    flip C  s7
vote(u1,D,DOWN); vote(u1,D,UP)    flip D  s9
getRecentUniqueFlips(u1) -> [D s9, C s7, A s5]    (B falls out)
vote(u1,B,DOWN)                   flip B  s10
getRecentUniqueFlips(u1) -> [B s10, D s9, C s7]
getRecentUniqueFlips(ghost) -> []
```

**What the interviewer checks**
- A `LinkedHashMap<articleId, FlipEvent>` per user, which works like an LRU cache keyed by article.
  - On a flip, `remove(articleId)` and then `put(...)`. That moves the article to the end.
  - When the map holds more than 3 articles, evict the oldest in O(1), using `pollFirstEntry()` (Java 21), `removeEldestEntry`, or `iterator().next()` followed by `remove()`.
- Reading: the map runs oldest→newest, so reverse it. In Java 21: `List.copyOf(map.sequencedValues().reversed())`.
- **Why not a `Deque`?** A deque can't find and remove a particular article in O(1) when it's flipped again. A `LinkedHashMap` gives you lookup by key **and** ordering.

## Follow-up discussion questions (with answers)

> How to answer: state **the specific failure**, then **the fix**, then **the trade-off**.

### 1. Concurrency
**Q:** 100 threads call `vote()` at the same time. Name two races in the current code. Compare `synchronized` on `vote()`, `ConcurrentHashMap`, and lock striping by `articleId`. Why doesn't `ConcurrentHashMap` alone fix it?

**A:**
- **Race 1: the previous-vote check, then act.** Two threads run `vote(u1, A, UP)` at the same time. Both read `prevVote = NONE` and both add +1, so the score counts the vote twice and two events are recorded.
- **Race 2: updating the score and its bucket.** Two different users vote on A at once. Both read `prevScore = 2`, both remove A from bucket 2, and then they add A to buckets 3 and 1. A ends up in two buckets, or its score disagrees with its bucket.
- **Also:** `seq++` isn't atomic, so two events can get the same sequence number. `ArrayDeque`, `TreeMap` and `LinkedHashMap` can be corrupted by concurrent writes.
- **Why `ConcurrentHashMap` isn't enough:** each single operation is atomic. But `vote()` changes **five related structures** (state, history, score, buckets and flips) that must stay consistent with each other, and no guarantee from one map covers a change that spans several.
- **Options:**
  - **`synchronized` on `vote()` and the readers:** correct and simple, but every vote waits for the previous one.
  - **`ReadWriteLock`:** many readers can run in parallel, and writers are exclusive. Good when reads dominate.
  - **Lock striping by `articleId`:** votes on different articles run in parallel. But a vote also touches user state, so you need user locks too, always acquired in a **consistent order** to avoid deadlock. Global top-K still needs its own lock.
  - **A single writer thread per shard** consuming a queue: no locks at all, ordered processing and easy reasoning. Readers use snapshots.

### 2. Durability
**Q:** The process crashes. How do you recover votes, scores and rankings? What must be persisted, and what can be rebuilt?

**A:** Separate the **source of truth** from **derived** data.

| Persist (source of truth) | Rebuild from it |
|---|---|
| Current vote per `(user, article)` | Scores (sum of the votes per article) |
| An append-only **event log** of votes, with sequence numbers | Top-K buckets (from the scores) |
| The sequence counter (or the log's maximum) | Last 3 votes, last 3 flips, unique flips (the tail of the log) |

- Write to a **write-ahead log (WAL)** before changing in-memory state. Take **snapshots** periodically.
- On restart: **load the latest snapshot, then replay the log entries written after it.**
- Or put the source of truth in a database: a `votes(user_id, article_id, vote, version)` table plus a `vote_events(seq, user_id, article_id, from, to, ts)` table. The in-memory structures become caches.

### 3. Idempotency
**Q:** A client retries `vote(u1, A, UP)` after a timeout. Is the system already idempotent? When would it not be?

**A:**
- **A plain retry is already idempotent.** A repeated `UP` is a no-op because the current state is checked first. That's a direct benefit of keeping state separate from history.
- **Reordering breaks it.** The client sends UP, times out and retries, then sends DOWN, and the delayed UP arrives last. The final state is UP, but the user meant DOWN.
- **Idempotency keys** (store processed request IDs with a TTL) catch **duplicate deliveries** of the same request. They don't fix **reordering**, because the delayed UP is a different request.
- **Fix for reordering:** the client sends a monotonically increasing **version or timestamp** for each `(user, article)`. The server applies a vote only if its version is newer than the stored one, and rejects stale writes. This is a compare-and-set on the version.
- Use **both**: keys for deduplication and versions for ordering.

### 4. Scale
**Q:** 10M users and 1M articles across many servers. How do you shard? Where does `getTopK` break, and how do you fix it?

**A:**
- **Shard user data** (current votes, user history, unique flips) **by `userId`**. **Shard article data** (score, flips) **by `articleId`**.
- **One vote updates both shards.** Avoid a distributed transaction: write the vote to the user's shard first, then publish an event to a stream partitioned by `articleId` (for example Kafka). A consumer applies the score delta to the article's shard. Article scores are **eventually consistent**, and the consumer must be idempotent (dedupe by event `seq`).
- **`getTopK` breaks** because no single shard sees every article.
  - **Scatter-gather:** each article shard keeps its own top-K, and an aggregator merges K × (number of shards) candidates. Cache the result for a few seconds.
  - Or a **Redis sorted set** maintains the global ranking: `ZINCRBY` on each vote and `ZREVRANGE 0 k-1` to read.
- **Hot articles:** one viral article makes its shard a write hotspot. Split its counter into N sub-counters (`A#0 … A#N`), choose one at random on each write, and sum them when you read.

### 5. Full history
**Q:** Product wants **all** of a user's votes, paginated. What changes in storage and API design?

**A:**
- **Storage:** an append-only `vote_events` table, **sharded by `userId`**, so one user's history lives on one shard and is read without cross-shard queries. Index it on `(user_id, seq DESC)`.
- **API:** use **cursor-based pagination**: `getVotes(userId, cursor, limit)` returns `{votes, nextCursor}`, where the cursor is the last `seq` seen. The query is `WHERE user_id = ? AND seq < cursor ORDER BY seq DESC LIMIT ?`.
- **Why not offsets:** `OFFSET n` gets slower the deeper you page, and new votes inserted between page requests shift the rows, so pages skip or repeat entries.
- **The in-memory "last 3" structures become a cache** in front of this query (`limit=3`), kept for low latency.
- **Retention:** with unbounded history, decide on archiving or TTL policies, and move old events to cold storage.
